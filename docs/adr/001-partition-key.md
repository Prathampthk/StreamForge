# ADR 001: user partition key (implemented Phase 2 producer)

Use tenant_id + ':' + user_id and Java-compatible murmur2 via franz-go StickyKeyPartitioner(nil). Alternative tenant-only keys preserve tenant order but concentrate large tenants. Random keys distribute load but lose user ordering. Ordering is per partition, not global or tenant-wide; concurrent requests can arrive in either order. Hot users still cause hot partitions. Adding partitions changes mapping and can break historical key ordering, requiring a controlled rollout. Retried publishes need client idempotence and ordering settings verified together. Producer tests verify repeated-key affinity, a hot-user key staying on one partition, and 12,000 users from one large tenant distributing across 12 partitions (800–1200 records each). This synthetic key test is not a throughput or realistic workload benchmark.
