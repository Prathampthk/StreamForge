# ADR 004: bounded broker-acknowledged ingestion (accepted Phase 2)

Use net/http and pinned franz-go, which defaults to idempotent production; explicitly require all ISR acknowledgments, preserve the client's safe sequence cancellation behavior, use Java-compatible keyed hashing, LZ4, 1 MiB batches and bounded buffered record/byte counts. No option permits disabling idempotence or changing acks. Metadata auto topic creation is disabled. Alternatives: kafka-go has simpler APIs but different idempotency support; a local queue returning 202 would violate the acceptance contract.

Each HTTP request is admitted without waiting into a bounded request set before reading its bounded body. One API key maps to one configured tenant in local mode, hashed before constant-time comparison. A bounded global token bucket returns 429; saturation returns 503. All elements of a batch are validated before producing any, but broker publication is not atomic. A partial/ambiguous failure returns 503 and may have published some or all records. Retry original immutable IDs. This phase does not deduplicate HTTP submissions or enforce cross-request ID/payload collision identity; the downstream Phase 3 correctness gate remains mandatory.

A producer promise owns its record and inflight metric until settled, even if the HTTP caller cancels. The handler can stop waiting on its deadline without breaking the producer sequence. The record buffer remains bounded; no goroutine is created per record. Delivery timeout is a safe-cancellation retry budget, not a hard bound on ambiguous idempotent writes. Closing the client after HTTP drain settles unresolved records as errors. No 202 is sent for an unresolved or failed promise. An error or disconnected response is an unknown delivery outcome, never proof of absence from Kafka.

Shutdown marks readiness false and stops new event admission before stopping listeners. Existing requests drain within the configured deadline; then canceled handlers/connections are closed, producer is closed and tracing is flushed with a fresh deadline. Kafka remains the acknowledged-event store; RF=1 only proves local behavior. Postgres is not queried on the hot path. Readiness checks Kafka metadata/topic partition count with a short deadline, while liveness never checks Kafka. Metadata readiness cannot promise the next write will succeed.

Metrics have finite outcome labels only; no IDs, tenants, raw paths or errors become labels. OTel spans cover HTTP and Kafka publish, with W3C context in headers. OTLP export is optional and sampled; sampling is tunable. No payloads or API keys are logged. The HTTP listener is local by default; Docker binds externally only through loopback-published ports. TLS and multi-tenant key management remain later hardening work.
