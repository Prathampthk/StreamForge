# ADR 007: measured resource and batching tuning (Phase 5)

The first 30-second, 1000-events/s pilot acknowledged all offered steady events, but produced 68 query failures despite low successful query latency. Actual ClickHouse exceptions were total-memory-limit failures near the 2GiB container cap. Its stock mark/uncompressed cache maxima were 5/8GiB. A higher-rate attempt failed readiness before steady measurement and is not reported as a completed load test.

Bound refresh execution to two threads and 256MiB/query, enable external aggregation at 64MiB, and cap caches at 128/64MiB. Reserve 4GiB for ClickHouse within the measured 7.75GiB Docker host and reduce background merge concurrency to four/ratio one. This is an explicit changed environment, not comparable proof of a gain at identical machine settings. Raw/state semantics, acknowledgments and validation remain unchanged. No data or volumes are deleted. Full-state recomputation still grows with history; spilling can exchange OOM for disk/latency cost.

The 30-second 10k offered pilot had low acknowledgment latency but successful freshness up to 22 seconds, censored failures and query failures. The original epoch collected only a global 128 records before dividing across 12 partitions, creating many tiny inserts and constraining backlog drain. Now collect up to the active-worker count times the per-partition batch limit while enforcing a global byte budget (including keys/headers/overhead), then process bounded partition chunks. A final fetch may overshoot the byte budget by one bounded fetch response. A larger twelve-partition epoch exceeded the single-worker processing budget in a scaling attempt, so the collection count now scales with active workers rather than total partitions. Each partition chunk stays <= configured batch records; at most configured workers insert concurrently, and all workers finish before commit/rebalance. Compose defaults to 1000 records/chunk and 8MiB global collection budget; host Go defaults remain 128/1MiB. New limits must remain inside the epoch/rebalance deadlines.

One-versus-three comparisons preload the same balanced 12-partition Kafka backlog, prewarm the same canonical IDs for both runs, pause fetching until all members are assigned, then time first insert through confirmed offsets with two query callers. Identical per-instance limits are used in both cases. This measures the consumer stage; it is not an end-to-end HTTP scaling claim. An initial comparison measured >2x commits but had query failures and an unbounded whole-canonical audit ran out of memory; its combined gate failed. Accepted-ID reconciliation is now chunked on the identity primary key, not a full payload-grouping scan with a post-group tenant filter.

Every report must distinguish successful latency samples from errors/censoring, offered/generated/HTTP-accepted/Kafka-acknowledged/persisted/aggregated counts, worker stage speedup from overall performance, and short pilots from the mandatory 15-minute result. Do not drop poison/unknown outcomes or disable durability to improve a number. Keep failed experiments and report resource/readiness limits honestly.

After the interrupted larger-history run, tried in-order identity aggregation before the approved fresh run. Pinned 25.8 EXPLAIN showed `AggregatingInOrderTransform`/`ReadPoolInOrder`; see the [official optimization guidance](https://clickhouse.com/resources/engineering/clickhouse-query-optimisation-definitive-guide). Actual execution still exceeded 256MiB reading payload states; 512MiB with 1024-row blocks/64KiB read buffers also failed (including total-memory pressure). This is an unsuccessful experiment, not an adopted speedup. Its SQL is retained in `load/ordered-refresh-experiment.sql` and is excluded from automatic migrations. Restored migration 003's bounded settings before the fresh run. Growing full-payload identity scans require a structural design change or a different measured resource envelope; increasing a query budget alone did not solve this host's limits.
