# StreamForge benchmark evidence

Targets are >=10k Kafka-acknowledged events/s for 15 continuous minutes, ingest p95 <100ms, concurrent query p95 <250ms, event freshness p95 <5s and >=2x consumer throughput from one to three replicas. The detailed [Phase 5 report](phase-5-report.md) separates measurements, errors and unverified guarantees.

Machine: Apple M4/10 cores/16GiB, macOS arm64, Docker 10 CPUs and 7.75GiB; all services and load generation share this host. Kafka 4.0.2, ClickHouse 25.8.4.13, PostgreSQL 17.6, Go 1.26.0. Single Kafka broker/12 partitions/RF=1, acks=all/idempotent/lz4. Consumer: one replica/four workers/1000 records per chunk/8MiB collection target. ClickHouse: 4GiB cap, two-thread/256MiB refreshes, 64MiB external aggregation. Batches of 100, 32 driver workers, seed 42, 60/20/10/10 page/cart/purchase/API mix, USD/EUR integer cents, 10% API errors. Two traffic query callers (15m/24h), sparse 1440-event historical seed and unique JPY visibility probes.

The first 900-second interval was **interrupted by confirmed host sleep**: 6.0474M steady acknowledgments, 6719.33/s across wall time, 3.4017M driver drops and 900 delivery-unknown events. Client p95 to headers was 311.2ms (body read omitted in that original driver); server histogram estimate 298.5ms. Query successes had p95 157.4ms but 8958/9350 requests failed. Seven successful probes had p95 29.65s, with 82 failed/censored and 510 dropped. It is not a continuous SLO result. Its receipt audit found no missing/hash-mismatched IDs among readable chunks, but 133k remained unverified, and aggregate totals failed reconciliation. No loss-free claim.

The corrected awake run recorded **9,301,900 acknowledgments in 900s = 10,335.44/s**, with no host sleep recorded: the Kafka-acceptance throughput target passed. There were 148,000 driver drops, zero unknown/rejected outcomes, full-response client p95 **248.58ms** and server p95 histogram estimate **232.01ms** (bucket upper 250ms): ingestion latency failed. **All 13,953 queries failed** and **all 124 probes failed/were censored**, with 775 dropped probes; successful query/freshness percentiles are unavailable, not zero. It started with ~6.57M physical identity-state rows and failed snapshot readiness, explicitly recorded; no healthy combined SLO pass. **All 9,303,564 accepted IDs and payload hashes were verified after load**, with zero missing/mismatched/unverified and 55 successful read retries. The ID audit temporarily paused failed refreshes, then restarted them before metric checks. **Revenue/traffic snapshots still failed exact reconciliation; overall audit failed.** Canonical persistence supplies no live-freshness or correct served-aggregate claim.

Consumer-only comparison (same 60k backlog, prefilled canonical state, 12 partitions, one worker/replica, concurrent queries): 1/2/3 replicas processed 9679.60/17240.00/18483.88 persisted+committed events/s. **1→3 = 1.90957x, below 2x.** No query errors; all 60k accepted IDs independently verified. Short isolated-stage timing is not end-to-end scaling.

Measured bottleneck: growing full-payload canonical recomputation hits refresh memory limits; ordered aggregation and a larger per-query budget were tried and failed, then reverted. Proposed next experiments: bounded recomputation of affected UTC minute/currency buckets with explicit conflict withdrawal, history lifecycle controls, and separating the driver from the service host. Each requires correctness/fault reconciliation and a repeated fixed-environment measurement; none is an achieved performance claim. Multi-broker/disk-loss durability remains unverified.
