# Event v1 contract

JSON Schema lives in schemas/event-v1.schema.json; validate with format checking enabled. Required identity is immutable. UUID format is accepted; generators should prefer UUIDv7. Tenant/user/order/session IDs contain only ASCII letters, digits, underscore and hyphen, at most 128 characters. A colon is therefore unambiguous in partition keys.

Limit encoded UTF-8 event bytes to 8192 before parsing (future HTTP boundary). Normalize parsed timestamps to UTC while retaining the original wire timestamp in Kafka. RFC3339 offsets are accepted. Proposed configurable policy: future skew <=5 minutes and lateness <=7 days at validation time. JSON Schema checks timestamp syntax; clock-relative windows require runtime validation in Phase 2. Old accepted events update their original UTC minute. Clocks must be synchronized; freshness starts at broker acknowledgment, not event time.

Attributes permit only source/device/campaign, at most three keys, 64 ASCII token characters per value. PII is prohibited by contract; syntactic restrictions cannot detect all PII. Currency syntax is three uppercase letters; Phase 2 must additionally validate membership in a pinned ISO 4217 list (schema does not claim semantic ISO membership). Purchase amounts fit signed Int64 cents, including zero; only valid purchase events contribute revenue. There is no failed-purchase variant in v1. API status is 100–599, API errors are >=500. Unused conditional fields are absent or null. Unknown fields and versions fail validation.

Revenue groups by tenant, UTC event minute, currency. Never sum currencies together. Traffic groups only by tenant and minute. RPM counts api_request events; events_per_minute counts all events; error_rate = errors/RPM, or 0 for an empty denominator. Queries must use sumMerge/countMerge with GROUP BY, even before background merges.

Topics: streamforge.events.v1 and streamforge.events.dlq.v1, each 12 partitions locally, RF=1. DLQ runtime is deferred. Future DLQ envelopes retain encoded original bytes, key/headers and Kafka coordinates, parseable event ID, sanitized failure code, component, retry count and failure timestamps. Transient outages must remain in retry/backlog, not DLQ.

Future HTTP/JSON v1: POST /v1/events succeeds only after broker acknowledgment; errors contain code/message/correlation_id and optional retry_after_seconds. 429 means rate limit, 503 means dependency saturation; both may carry Retry-After. Liveness is process-only; readiness is component-specific. APIs, auth, batch limits and query-window contracts are Phase 2/4 work, not implemented endpoints. Demo credentials must never be reused externally; raw API keys must never be stored in metadata.
