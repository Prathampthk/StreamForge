# Event v1 contract

JSON Schema lives in schemas/event-v1.schema.json; validate with format checking enabled. Required identity is immutable. UUID format is accepted; generators should prefer UUIDv7. Tenant/user/order/session IDs contain only ASCII letters, digits, underscore and hyphen, at most 128 characters. A colon is therefore unambiguous in partition keys.

Limit encoded UTF-8 event bytes to 8192 before parsing (enforced HTTP boundary). Normalize parsed timestamps to UTC while retaining the original wire timestamp in Kafka. RFC3339 offsets are accepted. Implemented configurable policy: future skew <=5 minutes and lateness <=7 days at validation time. JSON Schema checks timestamp syntax; clock-relative windows are validated by Phase 2. The consumer preserves backlog age and buckets accepted events into their original UTC minute without reapplying ingress wall-clock limits. Clocks must be synchronized; freshness starts at broker acknowledgment, not event time.

Attributes permit only source/device/campaign, at most three keys, 64 ASCII token characters per value. PII is prohibited by contract; syntactic restrictions cannot detect all PII. Currency syntax is three uppercase letters; Phase 2 validates membership in the pinned ISO 4217 snapshot (see currency-source.md); schema alone does not claim semantic ISO membership. Purchase amounts fit signed Int64 cents, including zero; only valid purchase events contribute revenue. There is no failed-purchase variant in v1. API status is 100–599, API errors are >=500. Unused conditional fields are absent or null. Unknown fields and versions fail validation.

Revenue groups by tenant, UTC event minute, currency. Never sum currencies together. Traffic groups only by tenant and minute. RPM counts api_request events; events_per_minute counts all events; error_rate = errors/RPM, or 0 for an empty denominator. Legacy append state queries use sumMerge/countMerge with GROUP BY but are diagnostic only. Final metrics read revenue_1m_canonical and traffic_1m_canonical, rebuilt from events_canonical; see ADR 003.

Topics: streamforge.events.v1 and streamforge.events.dlq.v1, each 12 partitions locally, RF=1. DLQ runtime is deferred. Future DLQ envelopes retain encoded original bytes, key/headers and Kafka coordinates, parseable event ID, sanitized failure code, component, retry count and failure timestamps. Transient outages must remain in retry/backlog, not DLQ.

Implemented ingestion HTTP/JSON v1: POST /v1/events succeeds only after broker acknowledgment; errors contain code/message/correlation_id and optional retry_after_seconds. 429 means rate limit, 503 means dependency saturation; both may carry Retry-After. Liveness is process-only; readiness is component-specific. See OpenAPI and ingestion.md for implemented POST /v1/events, POST /v1/events/batch, health, auth, limits and errors. Revenue/traffic query APIs are implemented on port 8082; see OpenAPI/query.md for minute-aligned half-open windows, exact string cents, separate query key and refresh-health rejection. Demo credentials must never be reused externally; raw API keys must never be stored in metadata.

Duplicate logical IDs can exist in Kafka, including same-ID/different-payload records. Producer idempotence only addresses internal retry sequences. Phase 3 canonical identity treats normalized equal payloads as one contribution. Different payloads quarantine the entire global identity visibly and exclude it from final metrics; any prior contribution is withdrawn on refresh. Legacy append aggregates are not final analytics. HTTP errors or disconnects are unknown outcomes; do not change event IDs when retrying.

## Phase 5 broker acknowledgment receipts

Successful ingestion responses additionally contain `acknowledgments`, one `{event_id, acknowledged_at}` per event. The timestamp is captured by the real producer's successful broker callback, using the ingest process clock; array order is not guaranteed. It is neither Kafka event time nor ClickHouse visibility. Measurement clients validate IDs/counts before treating the response as accepted. Failed/partial publication remains delivery-unknown. The v1 event payload contract is unchanged. DLQ envelope/replay operations are documented in [replay.md](replay.md).
