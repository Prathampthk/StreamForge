# Failure model through Phase 4

Verified local invariants: HTTP success follows Kafka acknowledgment; consumer commits follow synchronous raw+identity projection persistence; repeating or regrouping sink inserts does not multiply canonical metrics; conflicted IDs are explicitly excluded; failed/poison delivered records are never skipped by source commits. The test matrix and exact results are in phase-3-report.md.

Kafka RF1 and one ClickHouse host are non-HA. Named volumes survive process/container stop but host/disk loss, deletion, corruption, Kafka retention exhaustion and unclean administrative offset resets remain outside the verified guarantee. acks=all confirms ISR log acceptance, not per-request fsync. Broker-failure claims still require three replicas/RF3/min ISR2, safe election and a separate fault test.

A consumer can die before insert, after insert/before commit, while retrying an ambiguously acknowledged insert, or during rebalance. Its uncommitted offsets replay. Raw/MV partial insert results can leave extra physical evidence; complete immutable retries with insert dedup disabled eventually populate identity state before any commit. A lost successful response is an unknown outcome, so retry and compare canonical IDs instead of claiming raw uniqueness. Min/max full-payload state equality makes replay safe without a finite block-dedup window, global offset counter, PostgreSQL ledger or atomic Kafka/database transaction.

BlockRebalanceOnPoll protects bounded partition processing. Every worker finishes before allow-rebalance; serial commits include only successful partitions. Cancellation, generation loss, timeout or commit error never advances speculative offsets. Retry exhaustion exits for supervisor recovery/backlog retention. Poison records cause visible process failure with source coordinates, stop this member's forward progress and leave the failed batch uncommitted. Durable DLQ publish-before-commit and autonomous poison recovery remain Phase 5 work; there is no unsafe skip or transient-outage-to-DLQ path.

Logical-ID conflicts (including changed tenant/minute/currency) are retained in raw data and permanently visible through event_identity_conflicts. All variants of a conflicted identity are excluded from events_canonical. Snapshots retract its earlier contribution on their next successful refresh. This quarantine policy deliberately differs from silently choosing an arbitrary winner. Resolution/audit/replay automation is deferred. UUID normalization, optional-null equivalence and timestamp UTC normalization define logical equality.

Each metric snapshot replaces atomically, but revenue and traffic are not one transaction. A failed/slow refresh leaves previous values intact; fresh data remains in identity state. Until a successful refresh, readers may see stale data or a prior conflicting contribution. Inspect last_success_time/exception; do not advertise freshness from schedule alone. Identity states have no TTL, raw evidence expires after 30 days, and full-state refresh cost grows with lifetime unique events. A storage/retention/scale plan is required before external deployment or benchmark claims.

Migrations are initial rerunnable DDL, not upgrade reconciliation. PostgreSQL DDL is transactional; ClickHouse DDL is not, so rerun after partial failure. Concurrent migration runs are unsupported. Never edit an applied migration to change definitions. PostgreSQL down SQL is destructive and not invoked automatically. Legacy synthetic raw rows missing payload_json are not canonical facts; no guessed backfill was performed.

Phase 4 query responses fail closed on missing/failed/disabled/stale refresh metadata, bad rows, saturation and database timeouts. A successful refresh is not proof that Kafka backlog drained. Snapshot_last_success is the earlier metadata observation, not a later speculative version stamp or exact event acknowledgment-to-visibility measurement. Query authentication is one configured key/tenant locally; TLS/multi-tenant control-plane hardening remains Phase 6. Reconciliation trusts caller-recorded accepted receipts and an owned dataset scope, checks all bounded IDs/business values, and exits nonzero for discrepancies; it cannot recover unrecorded/unknown HTTP delivery outcomes.
