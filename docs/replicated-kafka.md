# Local replicated Kafka failure drill

Run `make replicated-kafka-test` or `python3 scripts/check-replicated-kafka.py --out <new-summary.json>`. Docker is required; AWS is not. The script creates a unique isolated Compose project with three combined KRaft broker/controller nodes, twelve partitions, RF3/minISR2, disabled unclean leader election and no published ports. The normal RF1 Compose stack is unchanged.

The Go fixture uses the real ingestion handler and Kafka producer. It validates per-event callback receipts, retains a private accepted-event journal, and compares every acknowledged ID and full Kafka payload. It first accepts 120 events, raises topic minISR to three, kills the partition-zero leader with SIGKILL and waits for every partition to reach ISR2. An unconfirmed twelve-event request must return 503. Restoring minISR2 while that broker remains down allows another 120 acknowledgments. After the killed broker rejoins ISR3, another 120 events are acknowledged. A different broker is then killed and the entire acknowledged cohort is read from the remaining brokers.

## Recorded result

The first local run passed in 58.163 seconds: **360 acknowledged events, 360 exact payload matches, zero missing IDs and zero duplicate acknowledged IDs**, spread across all twelve partitions. The twelve-event 503 request was treated as unknown delivery; **three of its IDs were observed**. This is direct evidence that failed HTTP acknowledgment does not prove absence from Kafka. [Small evidence](evidence/replicated-kafka.json) records topic overrides, broker IDs, phases, source hashes and cleanup. That run preceded its commit (`source_dirty=true`); the hosted CI check for that commit exposed a Linux bind-mount ownership issue. The runner now uses the invoking host UID/GID so private 0600 barriers remain readable without loosening their permissions.

## Boundaries and cleanup

All brokers share one Docker VM, network and administrative domain. This demonstrates broker-process crash/rejoin behavior with retained disks and a controller majority; it does not prove host, disk, power or availability-zone loss resilience. It does not test ClickHouse persistence or analytical deduplication and is not a throughput benchmark. The successful physical-duplicate check applies only to this producer session and fixture.

The runner compiles a race-enabled test binary using pinned Go, then runs it on the internal-only test network. Broker heaps are 256 MiB with 768 MiB container caps; the test client is capped at 1 GiB. If retained ClickHouse refreshes are active, it pauses only their schedules outside any benchmark and restores them in cleanup. The first run found no active retained server and paused none. No retained facts, identity tables, Kafka topics or volumes are deleted. Only the unique test project is removed with its three volumes; shared Go caches remain. Private results are kept under ignored `load/results/raw/streamforge-rf3-*`.

## Real-process shutdown coverage

`make process-shutdown-test` (or `python3 scripts/check-replicated-kafka.py --with-process-shutdown --out <new-summary.json>`) also builds the actual ingestion, consumer and query binaries with the race detector. It starts fresh isolated PostgreSQL and ClickHouse services, applies migrations, and sends SIGTERM to those binaries. The CI job runs this combined suite.

The ingestion cases stop acceptance while broker publication remains unresolved: restoring ISR permits a complete 202 receipt; keeping ISR unavailable yields `503 publish_unconfirmed`. Every acknowledged fixture payload is read back from Kafka. Unknown delivery is reported separately and its observed count is a lower bound from that read, not proof of absence.

The consumer is stopped after a confirmed ClickHouse insert and before committing Kafka offsets. A successful native offset fetch must show no positive commits on all twelve partitions. The replacement process must recover all ten fixture IDs, commit their offsets, and produce exact revenue/traffic totals despite physical replay duplicates. The failpoint is explicitly enabled only in that disposable child process. This tests graceful SIGTERM at the failure boundary; existing crash tests cover abrupt worker termination.

The query case holds a real ClickHouse revenue request in a local proxy, sends SIGTERM, checks listener closure, and then releases the request. Its exact response must finish before the process exits successfully. The disposable PostgreSQL cap is 512 MiB and the ClickHouse cap is 2 GiB, matching the existing CI analytics fixture. A preceding 1 GiB attempt failed with ClickHouse Code 241 and is retained privately; it is not counted as a pass. These are small correctness fixtures with default service deadlines, not throughput or retained-history readiness measurements. The harness also excludes synthetic canceled-poll error entries from real partition high-water accounting; an earlier attempt recovered all 360 IDs but failed on that bookkeeping error. The optional database volumes are removed with the owned test project; retained project data is untouched.

The combined local suite passed in **106.103 seconds** with no cleanup errors. Ingestion verified all 24 acknowledged payloads; its two shutdowns took 5.835s and 6.290s. Consumer restart recovered all ten fixture IDs with no premature commits, while 120 physical replay duplicate rows existed across the shared test topic; the isolated tenant still totaled exactly 10 events, four purchases, two errors, USD 200 cents and EUR 500 cents. The in-flight query returned exactly 200 cents and exited successfully in 1.017s. [Recorded evidence](evidence/process-shutdown.json) includes native offset results, environment and source hashes. This first passing run preceded its commit (`source_dirty=true`).

A later clean-source run on `41eb4e0` passed in **108.864 seconds**, with no cleanup errors: [verified evidence](evidence/process-shutdown-verified.json). It incorporates host UID/GID barriers, explicit source provenance instead of container Git stamping, immediate child-failure diagnostics, and bounded idempotent ISR setup against a confirmed live broker. A Linux run exposed an administrative setup timeout before ingestion started; the setup retry runs before the service workload, while publication/request/shutdown deadlines remain unchanged. The clean run observed 111 physical replay duplicate rows across the test topic and the same exact isolated-tenant totals.

The Linux [hosted reliability job](https://github.com/Prathampthk/StreamForge/actions/runs/42760799221/job/129645853963) also passed on clean `41eb4e0` in **201.122 seconds**, with no cleanup errors. Its Docker VM reports four CPUs and 16,759,300,096 bytes of memory. [CI evidence](evidence/process-shutdown-ci.json) is the summary extracted from that job's timestamped log, including source hashes, all 360 broker payload matches, all 24 ingestion payload matches, exact consumer totals and the drained query response. These durations describe the whole fixture, not SLO latency.
